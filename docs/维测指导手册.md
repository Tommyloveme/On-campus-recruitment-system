# 校招全流程管理系统 — 维测指导手册

> 本系统覆盖校招候选人从**登记、简历筛选、资审、笔试、面试、报批、谈薪、Offer 到入职**的全流程管理。

> 面向系统维护人员与测试人员，涵盖架构、配置、接口、数据库、部署、排障与测试方法。
> 用户操作说明见网页右上角「操作手册」（`static/manual.pdf`，由 `tools/gen_manual.py` 生成）。

## 1. 系统架构

### 1.1 运行视图

```
浏览器（原生 HTML/CSS/JS，无构建依赖）
   │  HTTP/JSON (Session Cookie 认证)
   ▼
waitress（多线程 WSGI，默认32线程） ── Flask 应用（app.py 入口 + campus/ 包）
   │
   ├── SQLite（data/candidates.db，WAL 模式）
   ├── 简历文件（data/resumes/<候选人id>_<随机>.pdf|.docx）
   └── 配置文件（config/ 目录，JSON 驱动）
```

- **技术栈**：Python 3.9+ / Flask / SQLite（标准库 sqlite3）/ openpyxl（Excel）/ mammoth（docx 转 HTML）/ reportlab（生成手册 PDF）/ waitress（生产 WSGI）。前端 Chart.js 已离线内置（`static/vendor/`）。
- **并发模型**：waitress 多线程 + 每请求独立 SQLite 连接 + WAL 日志模式（读写不互斥）+ busy_timeout 写锁等待，支撑 500+ 并发用户。

### 1.2 后端分层（五层，单向依赖）

后端 `campus/` 包按职责分为五层，**只允许上层引用下层，禁止反向或跨层跳跃引用**：

```
web (L4)      HTTP 接口层：Blueprint 路由、参数解析、鉴权装饰器、JSON 响应
   │
services (L3) 业务服务层：业务规则编排、SQL 读写、审计日志、文件 IO
   │
db (L2)       数据访问层：连接管理、建表 DDL、迁移、种子数据
   │
domain (L1)   领域规则层：纯函数业务规则（无 Flask、无 SQL、无文件 IO）
   │
core (L0)     基础层：路径/配置加载、日志、模块注册表、角色模板存取
```

各层职责与约束：

| 层 | 目录 | 允许依赖 | 禁止 |
| --- | --- | --- | --- |
| core | `campus/core/` | 标准库、config/*.json | 不得 import campus 其他任何层 |
| domain | `campus/domain/` | core | 不得出现 Flask / sqlite / 文件写入 |
| db | `campus/db/` | core、domain | 不得 import services / web |
| services | `campus/services/` | core、domain、db | 不得 import web，不得使用 Flask 的 request/session（`g.user` 由 web 层传入参数） |
| web | `campus/web/` | 所有下层 | 不得写 SQL（一律调用 services / db） |

**单一数据源原则**（改一处即全局生效）：

| 事实 | 唯一定义处 |
| --- | --- |
| 模块注册表（导航/权限的模块树） | `campus/core/modules.py` 的 `MODULE_REGISTRY` |
| 角色模板与新用户基线权限 | `config/roles.json`（`campus/core/roles_store.py` 读写） |
| 管理员判定 | `campus/services/acl.py` 的 `is_admin()`（admin 角色或 bypass=true 角色） |
| 流程阶段与字段 | `config/stages.json` + `config/stages/<stage>/fields.json` |
| current_stage 判定规则 | `config/master_import/registration/stage_rules.json` |
| 数据库表结构 | `campus/db/schema.py` 的 `SCHEMA` + `migrate()` |

### 3.2 阶段字段配置（刷新页面即生效）

字段定义位于 `config/stages/_common/fields.json`（公共）与各阶段 `config/stages/<stage>/fields.json`。

每个字段支持：`key`（内部名）、`label`（显示名）、`excel_column`（导入/导出表头）、`excel_aliases`（旧表头别名）、`type`（text/date/select）、`options`、`colors`（徽章颜色）、`visible`/`editable`/`importable`/`required`/`multiline`。

- **新增字段**：在对应阶段 `fields.json` 的 `fields` 数组追加一项；Excel 模板、表格列、编辑表单、图表维度自动联动。
- **删除字段**：从 JSON 移除；历史 JSON 数据中该 key 仍保留但不再展示。

### 3.3 主数据表导入配置

目录：`config/master_import/<页面>/`（当前仅 `registration`）。

| 文件 | 说明 |
| --- | --- |
| `index.json` | 数据源列表、全局导入开关、简历编号关联键、电话匹配键 |
| `stage_rules.json` | 按字段组合判定 `current_stage`；`values` 中 `*` 表示任意非空，亦支持通配符 |
| `sources/*.json` | 各 Excel 数据源列映射；表头支持 `match_patterns`（如 `*手机*`） |

主数据表导入为**全局**匹配，不提供模板下载。

### 3.4 角色模板（config/roles.json）

角色 = 权限模板。每个角色含 `key`/`label`/`bypass`/`perms`：

- `bypass: true`：绕过所有模块权限（系统管理员）。
- `perms`：`{module_key: {v,r,w,m}}` 模块权限映射；对用户「应用角色」时整体覆盖该用户的 module_acl。
- **新建用户的基线权限**取自 `user` 角色的 `perms`（`db/schema.py` 的 `_baseline_module_rows()`）。
- 界面「权限管理 → 角色」的增删改会写回本文件；`builtin` 角色不可删除。

## 4. 数据库

SQLite，建表语句集中于 `campus/db/schema.py` 的 `SCHEMA`：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | username, password_hash, role, department, job_roles, extra(JSON), **log_level** | 用户；log_level 为日志权限 1-10（管理员默认 1，普通用户默认 10） |
| `candidates` | data(JSON), phone(唯一), resume_file, current_stage | **原始数据预处理表**：两张原始表合并+预处理后的结果，全部业务页面读写此表 |
| `candidates_raw_manual` | phone(主键), data(JSON) | **手动录入原始表**：手动新增/页面编辑/Excel 导入的快照 |
| `candidates_raw_master` | phone(主键), data(JSON) | **主数据导入原始表**：主数据表刷新写入的行数据 |
| `module_acl` | subject_type, subject_id, module_key, perm_visibility/read/write/manage | **模块权限**：用户 × 模块四勾选 |
| `logs` | user_name, action, module_key, **level**, candidate_id, message | 操作审计日志（module_key 供各页面日志标签页过滤；level 为日志等级 1-10） |
| `interviewer_availability` | user_id, interview_type, avail_date, start/end_time | 面试官可约时段 |
| `interview_bookings` | interviewer_id, candidate_id, start_at | 面试预约记录 |
| `feedback` | user_id, title, content_html, priority, reply_html | 问题反馈 |

### 4.1 候选人数据管道（主键 = 电话号码）

```
candidates_raw_manual（手动录入原始表）─┐
                                        ├─ 合并（主数据优先）→ 预处理（current_stage 推导）→ candidates（原始数据预处理表）
candidates_raw_master（主数据导入原始表）┘
```

- **写入路径**：手动新增/编辑/Excel 导入 → `record_manual()`；主数据表刷新 → `record_master()`；两条路径都同步落到 `candidates`。
- **合并规则**：电话相同即同一候选人；以手动数据为底，主数据表非空字段覆盖（`merge_master_import_data`）；主数据锁定字段记入 `_master_locked_fields`，页面编辑该字段会被 400 拦截。
- **预处理**：`compute_current_stage()` 依据状态列推导 `current_stage`；候选人登记/校招流程（及子页面）/Offer策略（及子页面）/入职管理均基于该列过滤展示，各页面的更新写回 `candidates` 并同步 `candidates_raw_manual`。
- **删除**：`delete_candidate_row()` 级联清理面试预约、简历文件与两张原始表记录。
- **重建**：`candidate_pipeline.rebuild_candidate(db, phone)` 可按电话从两张原始表重新合并生成预处理行（维护用途）。
- **并发**：SQLite WAL + `busy_timeout=10s`（`db/connection.py`）串行化写入；`candidates.phone` 唯一索引兜底防止并发重复建档；raw 表以 phone 为主键 UPSERT 幂等，多用户同时操作同一候选人为「后写者胜」且全程有审计日志。
- **历史迁移**：`migrate()` 首次运行时把存量 `candidates` 回填为 `candidates_raw_manual` 基线快照。

- **升级兼容**：`init_db()` → `migrate()` 自动补列/建表。
- **自动备份**：启动后立即备份，之后按 `backup.interval_hours` 定时快照至 `data/backups/`；管理员可手动备份/恢复。
- **整机备份**：复制整个 `data/` 目录（建议低峰期；WAL 模式需同时复制 `.db-wal`/`.db-shm` 或先 `PRAGMA wal_checkpoint`）。

## 6. 权限模型

**纯模块授权模型**：`用户(工号) × 模块` 的 visibility / read / write / manage 四勾选，存于 `module_acl` 表；候选人数据为单一共享池（无用户分组/资源分组）。

- **模块树**：`campus/core/modules.py` 的 `MODULE_REGISTRY` 定义导航模块与「校招流程」下的子阶段模块；子模块权限缺省时**继承父模块**（`module_ancestor_chain()`）。
- **管理员判定**：`campus/services/acl.py` 的 `is_admin(user)` —— 用户 role 为 `admin`，或其角色在 roles.json 中 `bypass=true`。管理员绕过所有模块检查。
- **角色 = 权限模板**：`config/roles.json` 定义 admin / user / interviewer / manager（内置）及自定义角色；「应用角色」将模板 perms 整体写入该用户的 module_acl。新建用户自动按 `user` 角色写入基线权限。
- **接口防线**：web 层装饰器 `module_read_required("<module>")` / `module_write_required` / `admin_required`（`campus/web/guards.py`）；候选人级别的可见/可编辑过滤在 `services/acl.py`（`can_see_candidate` / `can_edit_candidate`）。
- **安全以后端为准**，前端按钮显隐仅为体验优化。
- 权限变更一律写入操作日志（action='permission'）便于审计；批量授予 manage 需 `confirm=true` 二次确认。

### 6.1 日志等级模型

- 每条日志有等级 `logs.level`（1-10，1 最敏感）；缺省按动作类型取 `campus/core/log_levels.py` 的 `DEFAULT_ACTION_LEVELS`（permission/user/backup=1、config=3、delete=5、import/export=8、其余=10）。
- 每个用户有日志权限 `users.log_level`（1 最高、10 最低），只能看到 `level >= 自己权限值` 的日志；系统管理员恒为 1（全部可见），普通用户默认 10（仅常规业务日志）。
- 设置入口：管理看板 → 操作日志 → 「日志权限」标签页（仅管理员）；各页面「日志」标签页同时受模块读权限与日志权限双重过滤。

## 9. 常见故障排查

| 现象 | 排查方向 |
| --- | --- |
| 端口被占用 | `scripts/status.bat` 或 `netstat -ano \| findstr :8000`，清理残留 python |
| 请求 404 但代码有路由 | 多个旧实例同时监听，force_stop 后重启唯一实例 |
| database is locked | 确认 WAL 已启用；检查外部工具长期占用写事务 |
| docx 预览 500 | 文件非真正 docx；提示下载原文件 |
| 修改 fields.json 后异常 | JSON 语法错误；key 重复或改名导致旧数据不显示 |
| 用户看不到某模块 | 「权限管理」检查该用户对模块的 visibility/read；子模块可由父模块继承 |
| 主数据导入全部跳过 | 检查双表是否都已上传；Excel 是否含简历编号/手机号关联列 |
| 会话全部失效 | `data/.secret_key` 被删除重建（正常现象） |

## 10. 代码导读（二次开发）

### 10.1 后端扩展路径

| 需求 | 修改位置 |
| --- | --- |
| 新增 API | `campus/web/` 新建或扩展 Blueprint；业务逻辑与 SQL 放 `campus/services/` |
| 新增流程阶段 | `config/stages.json` + `config/stages/<stage>/fields.json`；如需入导航/权限，在 `core/modules.py` 的 MODULE_REGISTRY 补一项 |
| 新增业务字段 | 对应阶段 `fields.json` 追加字段项 |
| 主数据表新页面 | `config/master_import/<page>/` 按 registration 结构复制 |
| 阶段判定规则 | `config/master_import/registration/stage_rules.json` |
| 数据库新表/列 | `campus/db/schema.py` 的 `SCHEMA` 与 `migrate()` |
| 新增角色模板 | 界面「权限管理 → 角色」或直接编辑 `config/roles.json` |
| 新增权限判定 | 一律加在 `campus/services/acl.py`，web 层只调用 |
| 新页面接入日志标签页 | 后端 `add_log(..., module="<模块key>")` 登记；前端容器上调 `renderLogPanel(el, {module})` 即可，无需新写日志 UI |

### 10.2 前端扩展路径

| 需求 | 修改位置 |
| --- | --- |
| 新侧边栏入口 | `static/js/main.js` 的 `buildNavStructure()`（模块 key 与 MODULE_REGISTRY 对应） |
| 新流程阶段页 | 一般无需改代码，`stage-view.js` 按配置渲染 |

### 10.3 分层依赖关系

```
app.py ── campus.create_app()
             │
             ▼
web/*  ──────────────► services/*  ─────► db/connection、db/schema
 │ guards（鉴权装饰器）    │ acl（权限中枢）
 │                        │
 └───────► domain/*  ◄────┘        domain：stage_routing / interview_slots / employees
                │
                ▼
             core/*                core：settings / modules / roles_store /
                                          stage_config / master_import_config / logging_util
```

**改代码前先问三件事**：

1. 这是不是纯规则？→ 放 `domain/`（可单测、无副作用）。
2. 要不要碰数据库/文件？→ 放 `services/`；web 层只留参数解析与响应。
3. 是不是新的"事实"？→ 检查第 1.2 节单一数据源表，改唯一定义处，不要复制。
